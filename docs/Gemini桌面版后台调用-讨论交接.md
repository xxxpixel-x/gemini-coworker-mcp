# Gemini 桌面版能否被其他 Agent 在后台调用？

**讨论交接 · 2026-11-22 · Windows 本机 · Gemini for Windows 1.21.1**

**同日后续实测**。用户明确的场景是 Gemini 处理任务时继续在 Codex 聊天。将 Gemini 主实例和收发程序放到独立 Win32 桌面后，真实握手与格式校验均已通过。用户桌面的前台事件检查也已通过。下面保留的是此前对普通桌面的测试记录。当前可用路径和重启步骤见[项目使用说明](../README.md)。

**原普通桌面测试的判断：本机测试的 Windows UI Automation（UIA）写入方式未通过后台验收。** Gemini 处于后台时，测试程序能找到输入框，也能写入文字；写入后观察到 Gemini 成了前台窗口。这一轮测试止于输入阶段，实际发送消息 **0 条**，收到真实回复 **0 条**。这足以决定当前安装应暂停普通桌面的自动派发。其他版本或其他受支持的桌面接口能否满足要求，仍是开放问题。

## 用户要解决什么问题

用户希望在 Claude Code、Codex、Antigravity 或 DeepSeekHarness 里说“把这个子任务交给 Gemini”，然后继续自己的工作。调用方向是 **宿主 Agent → 本机 MCP → 已登录的 Gemini Windows 桌面 App → 原宿主**。任务可以是写代码、补测试、起草文档或复核方案。网关已有任务和工作区工具，待解决的环节是桌面会话收发。

这里的“后台”有可观察的含义。用户在编辑器里连续打字时，字符应始终进入原编辑器；用户在 Gemini 个人对话里保留草稿、发送消息或切换聊天时，Agent 的消息和回复应始终留在它的专用会话。使用桌面 App 现有登录账号是产品要求。Gemini API、Gemini CLI、模拟键盘、借用剪贴板和抢前台再切回均已排除。

## 真机证据到哪一步

| 环节 | 当时观察到的事实 | 对讨论的意义 |
|---|---|---|
| 找到目标 | 启动后识别到官方 Windows App 的一个空白窗口。窗口标题为 `Gemini`，UIA 文档暴露的地址为 `https://gemini.google.com/app`。 | 可以识别应用与空白聊天页。能否在用户切换个人聊天后持续定位同一段 Agent 会话，仍待实测。 |
| 写入草稿 | 输入框报告支持可写的 `ValuePattern`。单行探测调用 `SetValue` 后，立即读回时尚未看到测试文字；约 600 毫秒后读回成功。 | 立即读取会漏掉异步更新；延长等待能确认文字到达，焦点仍须独立验收。 |
| 前台和剪贴板 | 写入前确认目标窗口在后台。采样显示前台窗口发生变化，随后只读核对确认 Gemini 已在前台；同次探测中剪贴板序号未变。 | 本轮未达到“不打断用户”的要求。现有采样不能精确指出哪个内部事件触发了激活。 |
| 发送与回复 | 首次握手停在发送前；单行复测只写草稿。最后只读检查确认测试文字已清除，编辑器回到空白占位状态。 | 后台发送、生成结束识别、完整读回、代码缩进保真和连续追问均未取得真机结果。 |

最后一次通过真实 stdio MCP 客户端查询，得到 `installed=true`、`running=true`、`version=1.21.1`、`login=unknown`、`background=unavailable`。本机 SQLite 的 `desktop_checks` 表记录了 `other-app` 场景的失败。13 项自动化测试已通过，其中桌面任务测试使用模拟回复驱动真实文件修改和验证命令；这些测试覆盖网关逻辑，真机结论以上表为准。[项目验收摘要](../README.md) · [任务集成测试](../tests/desktop.test.ts)

## 下一轮最值得讨论的两个问题

**1. 焦点变化是否可重复，发生在什么时刻？** 如果决定继续研究 UIA，最小的补充实验是做一次只读对照和一次单行写入对照。当用户在另一应用中输入时，两组都记录前台窗口和键盘焦点事件的时间戳，写入组额外标记 `SetValue` 的调用与返回。只需记录窗口标识和事件顺序，无需采集用户输入内容。若只读组稳定、写入组再次激活 Gemini，就有依据停止在这一写入路径上调整等待时间。Windows 提供前台事件订阅；UIA 控件声明的能力由应用提供者实现。[Windows 事件订阅](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwineventhook) · [UIA 控件模式](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-controlpatternsoverview)

**2. 有没有能按会话寻址、后台提交文字并读回结果的受支持入口？** 评估候选方案时，请给出接口文档或最小演示，并说明三个问题：怎样选择专用会话，怎样提交而不激活窗口，怎样确认收到的是本轮完整答案。Google 的 Windows 帮助页介绍了安装、登录和交互式问答，未说明这类程序化收发接口。参考项目 GeminiBastionMCP 展示了网页版 Gemini 调工作区工具的方向；它把任务派给 Gemini 时使用的是 CLI 驱动，不能用作 Windows 桌面后台收发的证据。[Google 桌面版说明](https://support.google.com/gemini/answer/18263854?hl=en) · [参考仓库的 Gemini 驱动](https://github.com/Kaiserunix/gemini-bastion-mcp/blob/182e0c1843fc2f6cd8becb944eed39369a532ab4/src/core/agentDrivers/geminiCliRunner.ts)

## 什么证据足以改变当前判断

| 场景 | 通过标准 |
|---|---|
| 用户在其他软件持续输入 | 专用对话完成一问一答；前台窗口、输入焦点、实际输入去向和剪贴板均符合预期。短暂抢焦点后恢复也计为失败。 |
| 用户同时使用 Gemini 个人聊天 | 在个人聊天保留草稿，并在任务期间发送或切换对话。Agent 在专用会话收到含随机标识、多行文字和缩进的完整答复；第二轮追问延续该会话。个人草稿和回复归属正确。 |
| 两个宿主连续派发 | 用不同请求编号提交两项任务，第二项在队列中取消。只有第一项出现在 Gemini，对应答案回到发起它的宿主。发送后若断线且无法确认结果，状态应为“待确认”，重连不重复发送。 |

**建议的讨论决策：** 在有候选方案能同时解释“怎么写入”和“怎么保持会话独立”之前，维持 `unavailable`。若候选方案需要用户首次手动创建专用窗口，可单独讨论这个一次性步骤是否可以接受；日常调用不干扰个人操作仍按上表验收。

接手时可先对照原生适配器中的 `Chat-Route`、`Same-Document`、`SetValue` 和 `Invoke`，再看网关如何分别报告安装与后台状态。只读的 `gemini_desktop_status` 可用来核对当前状态；README 中的绑定和验收命令可能写入草稿或发送固定测试消息。[原生桌面适配器](../native/gemini-uia.ps1) · [状态与请求管理](../src/core/desktopGateway.ts) · [绑定与验收说明](../README.md)
